# Сергей — кабинет собственника: техническое задание

Версия 1.0, 14 ноября 2026. Самостоятельный проект, не модификация AVERA. Заказчик — Сергей. Адресат документа — внешняя команда дизайна, frontend, интеграций и тестирования. Код реализации и этот документ передаются вместе.

## 1. Назначение и границы

За 60–90 секунд собственник должен понять: зарабатывает ли завод; хватит ли денег; какие заказы требуют внимания; где застряли деньги; какое решение требуется. Сначала объяснение и график, затем кнопка «Почему?» и раскрытие исходных строк. Не выводить ОСВ на первом экране. Не заменять отсутствие данных нулём. Расчётный прогноз не обозначать как факт.

Выпуск включает: самостоятельный сайт, интерактивный демонстрационный набор, рабочий режим, импорт нормализованного JSON, сервер приёма снимков и автоматического обновления, исходники, тесты, библиотеку визуальных компонентов и описание интеграций. Реальных подключений к 1С, банкам, CRM и производству без реквизитов и согласованных форматов нет. Публичная версия содержит только синтетические данные. Автоматическое создание проводок и проведение платежей не входят в задачу.

## 2. Исходный визуальный образец: измерение, а не исходный код

Исходник — JPEG 589 × 1280 растровых пикселей. Координаты ниже отсчитываются от левого верхнего угла, погрешность геометрии ±3 px; у теней ±8 px. DPR, CSS viewport, шрифт и код исходника неизвестны. Надписи с размерами на плакате неоднозначны; их нельзя принимать за достоверные CSS-токены. Это фотографический/рендерный образец, не снимок доступного DOM. Все CSS и JS в этом проекте восстановлены или спроектированы, а не извлечены.

Область плаката: x40…549, y160…1121, примерно 509 × 961. Наклон верхней грани и мягкое затемнение слева — свет и перспектива. Кнопки X (x11,y78,64×65), многоточие (x514,y78,64×65), нижняя надпись и домашний индикатор — интерфейс просмотрщика; в продукт их не переносить. Линейки на плакате относятся к демонстрации дизайн-системы, а не к навигации финансового кабинета.

## 3. Воспроизводимый CSS-контракт

Канонические значения — `public/styles.css`. Фон#e2dfd8, поверхность#e9e6df, текст#252923, вторичный#545a51, акцент#b4e0c9, акцентный текст#194c37, warning#ead79a, danger#edb3ac. Семейство Arial с системными sans-serif fallback: оригинальный font-файл отсутствует. Внешних шрифтов и CDN нет. Табличные цифры `font-variant-numeric: tabular-nums`.

Объём создаётся встречными тенями: наружная `9px 9px 22px #c5c2ba, -8px -8px 20px #fffdf5`; внутренняя `inset 3px 3px 7px #c5c2ba, inset -3px -3px 7px #fffdf5`. Поверхность — очень слабый диагональный градиент. Светлая верхняя рамка1px. Тени не являются единственным способом отличать кнопку от фона. Бордер функциональных контролов контрастнее декоративных карточек.

Desktop: максимальная ширина1440px, центрирование; sidebar204px, контент minmax(0,1fr), gap32px, поля32px. Карточки в двух колонках, gap26px. Радиус внешней панели28px, карточки24px, inset18px, кнопки999px. Вертикальный ритм8/12/16/24/32/48px. Заголовок страницы clamp(32px,4vw,48px), секций24px, вопроса28px, ответа24px, основного текста18px/1.5, служебного16px. Крупные деньги38–44px. Ни один пользовательский смысл не передавать шрифтом8px как в референсе.

На ≤1000px убрать боковую колонку, навигацию сделать горизонтальной с переносом; две карточки сохранять до760px. На ≤760px одна колонка, поля16px, gap20px. На320px поля12px, карточка padding18px, заголовки24px. SVG viewBox масштабирует геометрию, но подписи на узких экранах сокращаются и дополняются текстовым резюме. Не уменьшать основной текст ради размещения. При200% zoom — нормальный reflow.

Состояния: hover усиление светлой кромки; active inset; selected мятная поверхность и `aria-pressed`; focus-visible тёмное кольцо3px и светлый offset3px; disabled нативный атрибут, отсутствие события и пояснение. Hover не является единственным способом открыть данные. Min-height интерактивных элементов48px. Анимация только opacity/transform120ms; при prefers-reduced-motion отключить. Дизайн намеренно отклоняется от микротекста и низкого контраста снимка ради возрастных собственников.

## 4. Дерево экранов и поведение

AppShell → Sidebar(Обзор,Отчёты,Источники) → Header(период,крупнее текст) → неизменяемая метка демонстрации → резюме → карточки вопросов → список решений → дата/происхождение. В рабочем режиме без источника — честный пустой экран и действия загрузки. Страница `style-guide.html` демонстрирует цветовые плитки, тени, input, buttons, tabs, alerts и card как в плакате; это отдельный каталог, не главная страница собственника.

«Зарабатываем?» — месячная операционная прибыль, изменение к прошлому месяцу, сопоставление выручки с планом. «Хватит ли денег?» — минимум доступного остатка и дата; линия прогноза13 недель, ноль и согласованный резерв, подписи факта/прогноза. «Где застряли деньги?» — дебиторка по корзинам сроков, отдельно просрочка; не путать с НЗП. «Какие заказы требуют внимания?» — прогноз маржи по каждому заказу, отрицательные отдельно, ожидание оставшихся затрат.

Состояние JS: mode(demo/live/import), selectedPeriod, activeView, openDetail, detailTab, fontScale, snapshot, loadState, lastChecked, refreshError. Фильтр периода меняет все месячные блоки; прогноз имеет собственную дату и явно помечен. Диалог открывается по кнопке, получает фокус, закрывается Escape/кнопкой и возвращает фокус инициатору. Переключение «Пояснение / Строки отчёта / Источники» — кнопки с aria-pressed. Таблица допускает горизонтальную прокрутку внутри контейнера, не страницы. Данные вставлять через textContent/экранирование, без выполнения HTML источника.

Обновление: в live при открытии и каждые60сек, только видимая вкладка; один запрос за раз, timeout10сек, cache:no-store. Ошибка не уничтожает последний успешный снимок; рядом явно показать устаревание. Время проверки не подменяет дату данных. Смена source version перерисовывает согласованный снимок целиком; частично обновлённые карточки запрещены. Demo не запрашивает финансовый API. Локальный импорт не отправляет содержимое наружу и не записывает в Git.

## 5. Графики и расчёты

Прибыль: прямые столбцы реальных месяцев, нулевая линия; подписи периодов и единиц «млн ₽». Сравнение выручки с планом — парные столбцы, legend с текстом и разным заполнением. Нельзя дорисовывать плавную историю из двух накопленных итогов.

Ликвидность: линейные сегменты между недельными прогнозными точками, без сглаживания и overshoot; stroke3px, vector-effect non-scaling-stroke, маркеры4px; ноль темнее сетки, резерв пунктир4/4, основная линия тёмно-зелёная. ОсьY включает ноль, минимум и максимум с запасом15%; график не обрезает отрицательные значения. Минимум рассчитывать из всех точек и подписывать текстом вне SVG. Это минимум недельных остатков, не гарантия отсутствия внутринедельного разрыва. При одной точке показывать маркер; при пустом ряде — «Нет прогноза».

Просрочка: суммы счетов с dueDate раньше asOf; корзины «Срок не наступил /1–30/31–60/61+ дней /Срок неизвестен». Не учитывать неизвестный срок как непросроченный. Заказы: прогнозная маржа = (договорная выручка − фактические затраты − оставшиеся затраты)/договорная выручка. При нулевой выручке маржа не определена. Авансы не являются выручкой. Операционная прибыль = выручка − себестоимость − операционные расходы; чистая = операционная + прочий результат − проценты − налог. ДДС: конец=начало+операционный+инвестиционный+финансовый потоки. Баланс: активы=обязательства+капитал. Все суммы входа — целые копейки; округление только при показе.

## 6. Контракт данных и детализация

`public/model.mjs` — исполняемая проверка; `public/demo.json` — полноценный синтетический пример. Снимок содержит schemaVersion,id,generatedAt,asOf,currency,unit,isDemo,sources,months,cashForecast,receivables,orders,decisions. Каждый source имеет id,name,asOf,status. Месяц содержит period,status,sourceIds,pnl,cashflow,balance,equityBridge; order и задолженность — sourceId. equityBridge содержит начальный капитал opening и прочие изменения otherChanges; конечный капитал должен равняться opening + чистая прибыль + otherChanges. Начальный капитал и деньги следующего периода сверяются с концом предыдущего. Прочие изменения требуют расшифровки и основания в промышленном контуре. Все ссылки проверяются. Повторные id и периоды запрещены, месяцы должны возрастать; нужен хотя бы один месяц. Суммы, даты, монотонность прогноза, сверки трёх форм и ссылки проверять до отображения. Идентификатор снимка меняется вместе с содержимым. Unknown — null только в предусмотренных полях; отсутствие обязательной части не превращать в0.

Документы показываются в детализации как агрегированные строки отчёта. Переход до проводки/скана является следующим уровнем интеграции: в текущем JSON нет настоящих первичных документов, поэтому не рисовать фиктивные ссылки. Загрузка ОСВ напрямую требует маппинга аналитики конкретной конфигурации1С. Универсального достоверного «распознавателя любого Excel» не заявлять.

## 7. Архитектура обновления

Системы-источники → адаптеры только чтения → неизменяемые raw-файлы → проверка/нормализация → единые справочники → финансовые расчёты → сверки → утверждённый снимок → API → интерфейс. Репозиторий хранит код и demo; рабочие файлы хранятся вне public и исключены из Git.

Источники и методы:

- 1С: регламентная выгрузка XLSX/JSON из отчётов; затем согласованный HTTP-сервис/OData только чтение. Приоритет — ОСВ и журнал, аналитика заказов, НЗП, выпуск, взаиморасчёты, ОС. Не писать напрямую в SQL-базу1С.
- Банки: подписанные/проверенные выгрузки либо API банка с read-only правами. Сверять выписки с бухгалтерией, не дублировать оборот двумя источниками. Частота денег15–60мин при доступном API.
- CRM/Битрикс24: договоры, заказы, этапы, план оплат; webhook/API с курсором и повторной сверкой ночью. Сделка CRM не является фактом признанной выручки.
- Производство/MES/ERP: фактические операции, выпуск, брак, НЗП, оценка до завершения; по событию или раз в час. CAD/PLM даёт состав и версии изделия, а не фактическую себестоимость.
- Закупки/склад: обязательства, поставки, резервы; ERP/WMS или контролируемые XLSX, каждый час/день.
- Кадры/зарплата: агрегаты подразделений из ЗУП/учётки; после расчёта зарплаты, план отдельно. Не передавать персональные начисления в обзор владельца без необходимости.
- Excel/Google Sheets: утверждённые бюджеты и прогнозы с владельцем и версией; API/экспорт с проверкой схемы, не чтение произвольных ячеек по позиции.
- Документы/PDF/ЭДО: подтверждения и договоры; OCR только как предложение, существенные суммы и сроки проверяет человек.
- Займы/аренда/налоги: договорные графики и данные учёта; ежедневная сверка ближайших платежей.
- Ручные корректировки: автор, основание, согласующий, период и версия; отдельный слой, без переписывания исходника.

Реализованный адаптер первой очереди: JSON-снимок в закрытую папку inbox. Сервер сканирует каждые15сек, проверяет снимок, сохраняет неизменяемый архив и атомарно переключает current. Неверный файл помещается в rejected с отчётом; текущий снимок сохраняется. Дубли по хешу не создают новую версию. Это рабочий фундамент автоматизации, а не подключение перечисленных систем.

Промышленная очередь: адаптеры выгружают watermarks, source revision и deleted tombstones; идемпотентность по source+documentId+lineId+revision; повторные события безопасны. Late corrections повторно открывают расчёт периода и требуют утверждения. Справочники entity/order/contract/department/cost_item версионируются. Source of truth определяется по полю, конфликт не разрешается «последним файлом».

Для нескольких предприятий нужен PostgreSQL, транзакции, job queue, объектное хранилище, резервные копии и журнал аудита. SSO/OIDC и роли собственник/финансист/интегратор, ограничения по юрлицу. Уведомления владельцу источника при ошибке, dead-letter очередь, экспоненциальные повторы, метрики свежести и полноты. Плановые данные, фактические и утверждённые версии раздельны. Тест восстановления backup обязателен перед эксплуатацией.

GitHub Pages публикует статические файлы, не запускает закрытый сервер. Для факта использовать отдельный защищённый хост с TLS и серверной авторизацией. Включённая в прототип HTTP Basic защита предназначена для локального/закрытого стенда за TLS, не заменяет корпоративный SSO. GitHub Actions проверяет код; не хранит банковские/бухгалтерские выгрузки в артефактах публичного репозитория.

## 8. Приёмка и ограничения точности

Проверить320/390/768/1440px, клавиатуру, Escape, фокус, масштаб текста, отсутствие горизонтального скролла страницы, длинные названия и отрицательные суммы. Проверить demo/live, пустой API, неверный снимок, дубликат, недоступность источника, восстановление после ошибки, сохранение последней версии. Финансовые тесты: прибыль не равна поступлениям, нулевая выручка, отрицательная маржа, равенство баланса, кассовый разрыв и возврат выше нуля, неизвестный срок долга.

Цель доступности: основной контраст≥4,5:1, крупный≥3:1, интерактивная область≥48px — выбранное усиление относительно минимума WCAG. Не заявлять сертификацию только по автоматическим тестам. Основания: https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum ; https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum . Публикация: https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site .

Точность1:1 гарантировать относительно переданного HTML/CSS и зафиксированного браузерного рендера, а не неизвестного исходного DOM фотографии. JPEG, перспектива, освещение, неизвестный шрифт и сознательное увеличение элементов ограничивают сравнение с оригиналом. Снимок не содержит финансового dashboard layout: его сетка и графики спроектированы здесь. Референс определяет материал/палитру/объём компонентов; новые экранные композиции — реализация задания, а не извлечённый оригинал.
